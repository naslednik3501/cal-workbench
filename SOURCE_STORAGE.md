## Как устроено постоянное хранилище

1. **Исходные ZIP целиком:** пять вложений закрытого GitHub Release
   `originals-2026-11-02`. Имена вложений вида `archive-<12 первых знаков SHA>.zip`.
   Их размер и полный SHA записаны в `MANIFEST.json` хранилища.
2. **Индекс:** `indexes/by-name/xx.jsonl` для поиска по имени;
   `indexes/by-archive/<SHA ZIP>.jsonl` для полного перечня одного архива.
   Каждая запись хранит исходный путь, номер записи ZIP, размер и SHA-256 файла.
   Совпадающие имена и разные варианты сохраняются отдельно.
3. **Отдельные файлы:** `objects/xx/<SHA файла>.json`. Небольшие файлы находятся
   прямо в JSON как сжатые исходные байты в Base64. Большие используют перечисленные
   в JSON части `chunks/.../*.b64`. Это обратимое хранение, а не переработка CAL.
4. **Проверка:** при восстановлении проверяются размеры, части и конечный SHA-256.
   Пути из архивов не используются как команды и не извлекаются прямо в файловую систему.

Файлы с одинаковыми байтами хранятся один раз, но все их исходные пути остаются в индексе.
Большой файл не нужно держать в оперативной памяти целиком: восстановление потоковое.
Вложенные RAR/ZIP хранятся как отдельные исходные файлы; при необходимости скачивается
и разбирается только соответствующий вложенный архив.

## Правило для экономной работы

**Не скачивать все ZIP и не перечитывать весь каталог при каждом продолжении.**

Сначала прочитать этот документ, проверить статус публикации и доступ к закрытому
репозиторию. Затем искать конкретное имя, получать нужный объект и восстанавливать
только его во временную папку. Полные архивы нужны для повторной проверки упаковки
или инвентаризации всего источника. Получение данных всё равно происходит, но обычно
это один маленький индекс и один объект, а не 1 ГБ ZIP.

### Через подключённый GitHub в чате

- Выбрать фактический опубликованный commit из статуса; закреплять чтение на нём.
- Для точного имени вычислить первые два знака
  `sha256(filename.casefold().encode('utf-8')).hexdigest()`.
- Прочитать `indexes/by-name/<эти два знака>.jsonl` через `fetch_file`.
- Отфильтровать записи по точному имени без учёта регистра, затем выбрать нужные
  архив и путь. Не выбирать автоматически первый одноимённый CAL.
- Прочитать `objects/<первые два знака SHA>/<полный SHA>.json` и указанные части,
  если они есть. Сохранить ответы локально и восстановить Base64 → zlib → исходные байты.
- Проверить SHA-256 перед разбором. Готовый код восстановления — в `tools/source_store.py`.
- Если Contents API возвращает пустое содержимое большого индекса, читать Git blob
  по возвращённому SHA. Это не означает, что файл пуст.
- Сохранённая локальная копия — кеш. После потери кеша повторно получить только нужные объекты.

Доступ второго аккаунта ChatGPT не появляется автоматически: его GitHub-подключение
должно иметь доступ к тому же закрытому репозиторию. Перед использованием проверить
чтение MANIFEST и восстановление одного небольшого файла именно из этого аккаунта.

### Через локальные инструменты с уже авторизованным GitHub CLI

```sh
python tools/source_store.py find --repo OWNER/REPO --ref COMMIT --name "Sportage 95160.cal"
python tools/source_store.py get --repo OWNER/REPO --ref COMMIT --sha FILE_SHA256 --output /path/to/restore/file.cal
```

`get` не перезаписывает существующий файл. Команда `verify` проверяет всё хранилище;
не запускать её удалённо для обычной работы с одним калькулятором.

## Как завершить первоначальную публикацию

Скрипты используют Python стандартной библиотеки; публикация дополнительно требует
официальные `git` и `gh`, уже авторизованный GitHub CLI и доступ к GitHub.
В текущей облачной среде нет авторизованного CLI, поэтому эти команды публикации
здесь пока не выполнены. Не запрашивать пароли или токены в сообщениях.

```sh
python tools/source_store.py build --out /path/to/prepared-store /path/to/archives/*.zip
python tools/source_store.py verify --root /path/to/prepared-store
python tools/publish_source_store.py --repo naslednik3501/iprocal-sources --store /path/to/prepared-store /path/to/archives/*.zip
```

До публикации положить в корень подготовленного хранилища копию этого документа
как `README.md`, а в его `tools/` — `source_store.py`. Команда build требует пустой
каталог; уже подготовленное и проверенное хранилище повторно строить не нужно.

Публикатор сначала проверяет все входные ZIP и восстановление объектов локально.
Он создаёт private-репозиторий или принимает существующий пустой private-репозиторий,
затем загружает данные обычным Git и пять оригиналов как Release assets. Публичные
и непустые репозитории отвергаются. Передаются только файлы подготовленного формата
и указанные служебные инструкции. Токены не читаются и не записываются в исходники.

После загрузки сравниваются commit SHA и контрольные суммы Release assets. Если GitHub
не отдаёт SHA-256 вложения, публикатор скачивает его один раз и проверяет сам.
Результат записывается в `publication-result.json` рядом с подготовленным каталогом.
Скрипт публикации проверен синтаксически, но сквозная загрузка пока НЕ проверена.
При обрыве не запускать его слепо повторно: сначала проверить созданные ветки и assets;
скрипт специально не перезаписывает непустой репозиторий и не делает force push.

После успешной публикации: проверить выборочное получение через GitHub-подключение,
обновить статус и ссылки в рабочем репозитории и README нового репозитория.
Только после этого отметить источник как готовый для других чатов.
