## Откуда известно поведение

Использованы готовые `reports/T-005-binary-resolution-2026-11-04.md` и
`reports/binary-resolution-2026-11-03.json`. Старая ветка
`task/T-003-claude-fis` на `b72a159469048c65e784ef3588b38cb933a5c19c`
содержала только запись начала работы; опубликованной реализации и отдельного
исследования в ней нет. Ветка сохранена. Исследования T-005 и исходный
[дизассемблер ivanus0](https://github.com/ivanus0/iProg-script-disasm/blob/44ba11acfebc239bb704b50c7b7f4fef371c0784/cal.py)
использованы с действительным происхождением, выводы T-003 принадлежат указанному
исполнителю. Дизассемблер задаёт только `R=?D` и аргументы, чего недостаточно для
выбора генератора или диапазона.

Из сохранённого хранилища выборочно получен уже известный `iProgPro.exe`:
SHA `14a476590cc6b8f2396036cc4083087146263ab3c5d393c679883da234789f57`,
5 843 987 байт, commit оригиналов `ab589e2bad449d7a94275f8365c1d44e6f700cc6`.
Сверены все девять частей, SHA-256 восстановленного EXE. **EXE не запускался**:
использован только статический разбор PE и инструкций x86.

Найдена таблица диспетчеризации CAL по VA `0x78CC94`, перед ней сравнение
`cmp al,0x4f` по `0x44DB24`. Проверены соседние обработчики перемещения,
загрузки константы, CALL и строк, чтобы отделить этот интерпретатор от IPR/Lua.

- `table[0x4D] = 0x451DDD`: байтовый индекс результата и dword LE аргумент,
  аргумент расширяется нулём до int64 и передаётся в `0x40F660`.
- `0x40F660`: два последовательных вызова `0x40F4A0`; первый — младшее слово,
  второй — старшее, у старшего очищается бит 31. Вычисляется остаток int64 по
  аргументу через `0x408F10`. Для нулевого аргумента возвращается 0, но оба
  слова генератора всё равно потребляются.
- `0x40F450` и `0x40F4A0`: MT19937, 624 слова, шаг 397, инициализация
  множителем `0x6C078965`, twist `0x9908B0DF`, tempering 11/7/15/18 с масками
  `0x9D2C5680` и `0xEFC60000`.
- При запуске события `0x44DA1F` вызывает `0x414500`, который берёт seed из
  `GetTickCount` через stub `0x401020`, IAT `0x8BF9EC`. Поэтому результат не
  определяется одним BIN и не должен подменяться фиксированным индексом.

Точная операция для поддерживаемого dword-аргумента:
`R[dest] = (((word2 & 0x7fffffff) << 32) | word1) % bound`, при bound=0 — 0.
В JavaScript остаток вычисляется через BigInt, чтобы не терять биты выше 2^53.
В браузере используется его миллисекундный таймер, поскольку Windows uptime
GetTickCount там отсутствует. `randomSeed` фиксирует этот внешний вход в тестах;
при одинаковом seed поток совпадает, при повторном нажатии с другим временем
может выбираться другой код, как и в оригинале. Генератор локален событию;
транзакции и разные VM не разделяют его изменяемое состояние.

Байты, VA, file offsets, хеши диапазонов и листинг девяти фрагментов:
`reports/T-003-native-proof-2026-11-04.json`. Проверка воспроизводится
`python tools/analyze_t003_native.py --exe /path/to/iProgPro.exe`
(исследовательские зависимости pefile/capstone; для сайта не нужны).

## Сопоставление четырёх оригиналов

Все четыре вызывают `0x4D 0xFF 0x0000001C`: `R255 = ?28`, затем копируют результат
в R10 и выбирают литеральные таблицы. Поддержаны обе исходные схемы трёх копий:
`0x10/0x20/0x30` и `0x20/0x40/0x60`, по восемь байт в каждой копии.
В каждой таблице исходника есть 29 записей (индексы 0..28), но остаток по 28
даёт только 0..27: запись 28 с сообщением «Новый код 0926 записан.» недостижима.
Она сохранена как в оригинале, предел не менялся ради её включения.

`tools/analyze_t003_fis.js` сверяет SHA, весь достижимый граф, аргументы 0x4D,
58 исходных ветвей каждого файла, все 24 литеральных байта в каждой ветви и
соответствующее сообщение. Обе схемы и все четыре версии содержат одинаковые
табличные байты и сообщения, несмотря на разные формы/адреса событий.
Закреплённый результат — `tests/fixtures/t003-fis.json`.
