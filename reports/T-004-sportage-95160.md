## Результат и границы

Сохранённая версия CAL уже распознаётся текущим движком. Изменение декодера или
расчётной логики для её выполнения не потребовалось. Выполнено 10 групп проверок,
в том числе 152 сравнения полного выходного буфера с отдельной формулой записи.
Проверены чтение, округление, оба варианта записи, контрольная сумма, граница
ввода, сохранность исходника и откат незавершённой транзакции.

Это проверка текущего интерпретатора против вручную разобранного алгоритма этой
версии CAL на искусственных BIN. Независимых результатов оригинального iProg,
подходящего реального дампа и проверки физического блока нет. T-004 не следует
считать полностью завершённой проверкой применимости к автомобилю. В рабочий
каталог CAL не добавлен; оригинал из закрытого хранилища публично не скопирован.

## Разобранный алгоритм

Форма прямо описывает калькулятор пробега KIA Sportage, панель Yazaki,
EEPROM 95160. Есть одно числовое поле, сообщение и ссылка `Kia.bmp`.
Исполняемые события работают с байтами загруженного буфера; аппаратных команд
среди разобранных инструкций нет. Для T-001 это содержимое относится к расчётам
по готовому дампу. Соответствие изображения ещё не устанавливалось.

`OnShow` читает только первую шестибайтную запись `0x4C..0x51`. Первые два байта
образуют беззнаковое little-endian слово. Контрольная сумма равна младшему байту
суммы первых пяти байтов плюс `0xAA`. При совпадении с шестым байтом поле получает
слово × 15 и выводится «Дамп ОК. Введите новый пробег.». При несовпадении поле
обнуляется и выводится «Неверный дамп!». BIN событие не изменяет.

`OnApply` принимает значение до 983000 включительно. Для большего значения
исходный CAL выводит предупреждение и заканчивает работу без записи.
Для допустимого значения `q = floor(пробег / 15)` записывается 40 одинаковых
шестибайтных записей, начиная с `0x4C`, с шагом 6, до `0x13B` включительно:

| Смещение в записи | Значение |
|---|---|
| 0, 1 | `q`, младший байт первым |
| 2, 3, 4 | `00 00 00` при чётном `q`; `E0 FF FF` при нечётном |
| 5 | `(сумма байтов 0..4 + 0xAA) mod 256` |

Все байты вне `[0x4C, 0x13C)` остаются прежними. Повторное чтение возвращает
`floor(пробег / 15) × 15`: например, 100000 → 99990 и 983000 → 982995.
Округление следует из исходных команд, оно не исправлялось.

Адреса кода для проверки вывода: `0x138..0x1E8` — чтение/проверка первой записи;
`0x297..0x2BD` — верхняя граница и деление на 15;
`0x2C0..0x2E4` — копии слова;
`0x2E4..0x352` — выбор трёх байтов по чётности;
`0x352..0x3AF` — сумма и её копии;
`0x3AF..0x3C4` — сообщение об окончании.

## Существенные ограничения самого CAL

1. «Дамп ОК» означает совпадение суммы только первой записи. Остальные 39 записей
   не проверяются при чтении. В тесте испорчены сумма второй и данные последней
   записи, но исходный CAL продолжает выдавать «Дамп ОК».
2. `OnApply` рассчитывает исходную сумму и сравнивает пары байтов
   `0x155 ↔ 0x39`, `0x156 ↔ 0x34`, `0x157 ↔ 0x30`, однако результаты этих
   вычислений не используются как условие отказа перед записью. Даже после
   сообщения «Неверный дамп!» допустимое число можно записать. Это обнаруженное
   поведение исходного алгоритма в существующей модели VM, а не добавленная
   проверка совместимости.
3. Точного ограничения на размер EEPROM в CAL нет. Максимальный адрес чтения
   в `OnApply` — `0x157`; буфер 344 байта уже позволяет выполнить этот код.
   Это техническая граница доступа, **не допустимый размер EEPROM и не совет
   дополнять реальный дамп**. Основные проверки используют синтетические 2048 байт.
4. Предупреждение о значении выше 983000 — обычное завершение события, не
   исключение VM. Отдельная предметная проверка подтверждает отсутствие записи.
5. Проверка по той же формуле и обратное чтение не доказывают правильность выбора
   CAL для конкретного автомобиля или эквивалентность исходному iProg.

Эти ограничения зафиксированы тестами без изменения общих обработчиков.
Перед добавлением в каталог нужно решить, какие дополнительные ограничения
применимости обоснованы достоверными данными. Нельзя молча объявить исходное
«Дамп ОК» полной проверкой файла.

## Воспроизведение

Оригинал намеренно передаётся тесту внешним аргументом, чтобы он оставался в
закрытом хранилище. Тест проверяет SHA до разбора и откажется от другого CAL.
Из корня приложения, с доступной локальной копией хранилища:

```sh
python tools/source_store.py get --root /path/to/iprocal-sources \
  --sha 1544ac94267414e7aebae42bfc455d1699df96e60417469dcdeb118e0770fffa \
  --output /private/cache/Sportage-95160.cal
node tests/test_sportage.js /private/cache/Sportage-95160.cal
```

Для удалённого выборочного получения вместо `--root` использовать
`--repo naslednik3501/iprocal-sources --ref ab589e2bad449d7a94275f8365c1d44e6f700cc6`
с уже авторизованным `gh`, как описано в SOURCE_STORAGE.md. `get` не перезаписывает
существующий файл. Ни одного пользовательского BIN тест не требует и не сохраняет.

Фактический запуск: Node v24.19.0; **10 групп PASS, 152 расчётных вектора**.
Вектора включают округление, обе чётности, перенос между байтами, 983000,
отказы выше предела, неверную сумму, несовпадающие проверяемые байты, короткие
буферы и откат после лимита выполнения. Полные выходные массивы сравниваются
с отдельной формулой, которая не вызывает интерпретатор и не воспроизводит
его регистры или поток инструкций. Проверки относятся к текущей беззнаковой
модели VM.
